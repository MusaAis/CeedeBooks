**v1.3.2.3: Phase H, piece 3, the agent's release path for a milestone escrow (built; run live once on Oct 28)**
- New `agent/escrow_release.py`. The verdict is written by code only, with no model: release when the escrow is not paused, the milestone amount is within the escrow's own agent limit, the escrow holds at least that amount and the evidence pull request is merged; escalate when the amount is above the limit (the agent sends nothing; only the approver can release it, from their own wallet); hold when the escrow is paused, short of funds or the pull request is not merged. A request that is not a decision (a milestone that does not exist or is no longer pending, an escrow whose agent is not this business's wallet) is refused and recorded nowhere
- A release sends exactly two transactions from the business's own agent wallet: `commitDecision`, then, once that is confirmed, `releaseMilestone`. The commitment is `keccak256(abi.encode(escrow, chainId, index, evidenceHash, reasoningHash))`, the contract's own formula; the agent never sends an override, reject, withdraw, pause or role change
- The decision is hashed, chained into the business's signed ledger and stored before the first transaction (actions `ESCROW_RELEASED`, `ESCROW_ESCALATED`, `ESCROW_HELD`; hash format 2; the text carries the evidence facts, so the evidence hash can be recomputed from the record). Escrow decisions are not counted in the paid, held and escalated figures, the outcomes or the traction
- New routes, all wallet-signed admin: `POST /admin/escrows/{id}/milestones/{index}/decision` (a dry run that writes nothing and returns the evidence hash), `POST /admin/escrows/{id}/milestones/{index}/release` (it must present that hash and is refused if GitHub now says something else) and `GET /admin/escrows/{id}/releases`. New table `escrow_releases`, one row per milestone, claimed before anything is sent so two clicks cannot both release; a failed attempt can be retried, a claim left by a crash expires after 5 minutes, and a confirmation that times out is settled by reading the chain
- `GET /decisions/{hash}/verify` now finds the `MilestoneReleased` event on the registered escrow (it is on that contract, not on the business's budget contract); a record naming an escrow that belongs to another business is not confirmed. `agent/escrow_chain.py` gained one read, `release_events`, and is still unable to send a transaction
- Tests: 51 new Python tests (693 in total), all passing. Seventeen guards were broken on purpose (the limit boundary, the pause check, strict `merged`, the funding boundary, the chain binding, waiting for the commit, flagging a refusal, the evidence-hash echo, the claim, the retry and expiry rules, the agent-role and pending checks, the event the record is checked against, the owner check) and each break failed a test; one gap (the owner check) was found and fixed that way. The commitment was also compared with the value the real `MilestoneEscrow` returns from `commitmentFor` on a local node, and the whole path (commit, release, the event read back, an over-limit release refused by the contract, a second release refused) was run against a real local copy of the contract with Circle replaced by a local sender. The 111 Foundry tests are unchanged and were not rerun
- New table is created on first start; nothing existing changes, no hash-format change, no contract change and no public figure moves. The proof page shows an escrow decision as `ESCROW_RELEASED`, `ESCROW_HELD` or `ESCROW_ESCALATED` in the feed
- New **Escrows** tab in the admin site: register an escrow, see its balance, limit and milestones, add funds from the owner's own wallet (a USDC transfer, after a confirmation), run the dry run and press Release. Release is refused by the page until a dry run with the same milestone and pull request has been shown, it carries the evidence hash from that dry run, and the owner's wallet sends nothing for it (the agent wallet does). After a release the page checks the record and the on-chain event. 14 new checks in `admin/admin.test.js` (also run as a second business); seven guards of the tab were broken on purpose: six were caught (one gap, the display of an unmerged pull request, was found and fixed that way) and the seventh, a zero-amount check, is also enforced by the wallet helper
- **Run live on Oct 28** ([record](docs/rollouts/2026-10-28-escrow-release-live.md)), after the release was deployed to the server and before it was tagged: the reference escrow was registered from the Escrows tab and funded (0.5 and then 5 USDC from the owner's wallet); a hold (an unmerged pull request) and an escalation (milestone 2, above the limit) were recorded and sent nothing; then milestone 0 (0.1 USDC) was released with merged pull request 937 of `foundry-rs/forge-std` as a stand-in input: commit `0x73ac7434...a22421f0`, then release `0xc49c13dd...b83f1f` in block 69485148, both sent by the agent wallet. `GET /decisions/{hash}/verify` returned `verified: true` with an on-chain `MilestoneReleased` match. Not run live: a reject, an override, a withdraw, a pause, a release the contract refuses, a failed or timed-out confirmation, a retry, and a second business
- Not in this release: override, withdraw and pause actions for an escrow in the admin site (the approver can still send them from their own wallet), a proof-page view of escrows, and anything that reads evidence other than a GitHub pull request

**v1.3.2.1: Phase H, piece 2, evidence fetch rules, escrow reads, registration and a GitHub evidence dry run (built; the escrow read and the GitHub fetch were run live on the server)**
- New `agent/safe_fetch.py`: the only way the server fetches evidence. https on port 443 to `api.github.com` only; every address the name resolves to and the address the connection actually reached must be public (private, loopback, link-local, shared, multicast, IPv4-mapped, NAT64 and 6to4 addresses are refused); no redirects, no proxy from the environment, a 256 KB cap and a 6-second limit. A peer address that cannot be read is refused. Callers cannot pass a URL: `agent/evidence.py` builds it from a validated owner, repository and pull-request number
- `agent/evidence.py` turns a pull request into facts (repository, number, merged, merge time and commit, base branch, author) and an evidence hash, the SHA-256 of those facts in canonical JSON. The title and other free text never enter it; an unexpected shape is a failure
- New `agent/escrow_chain.py` (read-only; it cannot send a transaction) and an `escrows` table. Routes: `POST /admin/escrows`, `GET /admin/escrows`, `GET /admin/escrows/{id}`, `POST /admin/escrows/{id}/evidence-check`, public `GET /escrows` and `GET /escrows/{address}` (see the API table). Registration is accepted only if the contract itself ties the escrow to the signed-in business; another business's escrow answers 404
- Checked on the live server on Oct 27: the escrow read matches the deployment; a real merged pull request gave facts and a hash that recompute from the public pull request; pull requests that do not exist failed with the GitHub 404; `GET /escrows` answered an empty list. The wallet-signed routes were not run live (no admin screen yet). [Record](docs/rollouts/2026-10-27-escrow-reads-and-evidence.md)
