# Features

Everything the product does today, then what is planned and not built. Phase status is in the [roadmap](roadmap.md).

**Built and running**

- **On-chain budget enforcement**: per-transaction, per-day, and cumulative per-category-per-day spending caps, enforced by the contract itself, not by the agent's instructions
- **Vendor registry**: only approver-registered addresses can be paid; changing a vendor wallet requires explicit approver action
- **Commit-then-pay**: the agent's reasoning hash is committed on-chain in an earlier block than the payment it justifies, confirmed before the payment fires, so "reasoned before paid" is provable from block order
- **Escalation workflow**: the agent can park a payment for human review instead of guessing; only the approver can release it, exactly once
- **Three-way match**: an invoice must match a purchase order (number and amount) and an independently confirmed receipt, and the invoice wallet must match the vendor on file
- **Independent receipt witness**: a receipt confirmed by the `agent` role is rejected at the API and again inside the match
- **Rules-baseline decision engine**: deterministic pay / hold / escalate decisions. The language model writes the narrative only when the rules escalate an unregistered vendor (with figures filled in by code, see Oversight below), and gives a recorded second opinion on each decision; it never acts
- **Retry-safe payments**: before doing anything, the pipeline asks the contract whether the invoice key is already paid, so a crash-and-retry cannot pay twice
- **Confirmed, not assumed, settlement**: every commit, payment, and escalation is polled to a terminal on-chain state before it's recorded as succeeded — a reverted transaction is never logged as paid
- **Audit trail with round-trip check**: every decision (paid, held, escalated) is stored with its exact serialized hash input; `GET /decisions/{hash}/verify` recomputes the hash
- **Public proof page** (`ceedebooks.xyz`, no login): live paid / held / escalated counts, an Outcomes block, a feed of recent decisions, and a Verify button that recomputes the hash in the browser and checks it against the on-chain event
- **Refusals shown first-class**: held decisions are anchored on-chain with `logDecision`, and the page counts holds and escalations next to payments
- **Invoice pre-flight**: `POST /invoices/preflight` is a dry run that says whether an invoice would be paid, held or escalated, and why, without writing anything
- **Agent manifest**: `GET /.well-known/agent.json` describes the vendor flow, roles and guarantees for other agents
- **Wallet-signed admin site** (`admin.ceedebooks.xyz`): a session is accepted only if its signature recovers to the contract's current `approver()`; vendor approval, POs, receipts, escalations, limits and pause (with a reason) are signed in the admin's own wallet
- **Vendor portal** (`portal.ceedebooks.xyz`): a vendor applies with a wallet signature that proves it controls the payee address, the admin reviews the application, and once approved the vendor signs in with the same wallet. It sees only its own purchase orders and invoices, runs a dry run first, submits, and links to the proof page for the decision. No key or password is issued, and the portal never asks for a transaction. Spam controls: one pending application per wallet, at most 3 pending per IP, 5 submissions per hour per IP, small body cap
- **Shadow mode** (tested with mocks; no outside business has run it): a real bill is mirrored as a testnet payment only after the owner approves it. See [Shadow mode](how-it-works.md#shadow-mode)
- **Multi-business (v1.2.8 to v1.2.8.2):** `BudgetFactory` creates one `BudgetEnforcer` per business from the owner's own wallet, and every key, session, record and query belongs to one business, with cross-business denial tests. A business applies with a wallet signature at `portal.ceedebooks.xyz/business.html`, the operator accepts it (the server creates the business's hosted agent wallet), and the owner creates the contract with one transaction from their own wallet and picks their own limits. The server activates the business only after verifying the creation on-chain. The owner gets a setup checklist and an Add funds button in the admin site, and only the operator can mark a business as an outside party. One test business of ours has been through this on testnet
- **Signed hash-chained ledger (v1.2.9):** per business, each decision is chained to the previous one and signed with an Ed25519 key; `GET /ledger/verify` detects edits, deletions, reordering, forks, a wrong key and decisions added behind the chain's back. If the key is missing the agent refuses to log and so pays nothing. Since v1.2.9.2 the head is also anchored on-chain (next item)
- **Model-versus-rules log (v1.2.9.3):** each invoice decision records the rules' verdict and the model's own `{action, reasoning, confidence}` on the same facts, inside the hash (format 3). The rules verdict is the only one that acts; the model can neither release nor block a payment, and waits at most 3 seconds. No model, a timeout or an unusable answer is stored as null, and agreement is counted only where a model answered. Model text may hold words, not figures the code did not provide. `contract_refused` is set when a transaction for the decision reverts on-chain. `GET /metrics/decisions` gives totals, compared, agreed, disagreed and refused by origin and business, with live and shadow kept apart
- **On-chain ledger anchor (v1.2.9.2):** each business's agent wallet sends `LedgerAnchor.anchor(head, sequence)` every 25 new entries or 6 hours, whichever comes first, and only if the head moved. A failing job is logged and never blocks a decision or a payment. `/ledger/verify` returns the newest anchor for that business's `agent()` and fails if the anchored head is not in the chain at that sequence or the chain is shorter than the anchored sequence. The first anchor of each business is sent by hand with `scripts/anchor_ledger.py`; the job is off unless `LEDGER_ANCHOR_AUTO=1`
- **Owner-created categories (v1.2.9.1):** each business keeps its own category names; the owner adds one in the admin site's Limits tab (the server picks the next free id), then signs `setCategoryDailyLimit` from their own wallet. A category takes purchase orders and invoices only while its on-chain limit is above zero and readable, and another business's categories are never visible or usable. Names can be renamed; ids never change
- **Entered invoice amounts (v1.2.9.1):** no form or API field defaults an amount. The admin and portal forms fill in the purchase-order amount so it is visible, and the submitter can change it; a difference of more than 0.01 USDC escalates
- **Return to agent and re-run (v1.2.9.4):** on a multi-business (v2) contract the owner can send `reopenEscalation` from their own wallet; the server checks the `EscalationReopened` event carries that invoice's own reasoning hash, then runs the stored invoice through the same pipeline again (new reasoning, new hash, every limit and check). An invoice that ended in `error` can be re-run from the admin site; each takes one atomic claim, so two clicks cannot start two runs. The original v1 contract has no `reopenEscalation`, so there you can only approve or reject
- **Red-team script (v1.2.9.4):** `scripts/red_team.py` makes the agent wallet try to pay a non-approved address and expects the contract to refuse; the refusal is kept as a `contract_refused` row and the ledger head is anchored. It asks for `yes` before every on-chain step and fails loudly if the contract accepts. It was run live on Oct 15 and the contract refused (see [Traction](traction.md))
- **Archive flag (v1.2.9):** the operator can archive a business: it becomes read-only, leaves the public lists and totals, and its ledger still verifies
- **Gateway balance (v1.2.10):** the admin Overview shows the USDC balance Circle Gateway holds for the business's agent wallet on Arc (`POST /v1/balances`, no key needed). The card is a read only: the service never deposits, spends or decides from it (a deposit is the manual script in the next item), and if Gateway cannot be read the card says Unavailable, never zero
- **Gateway deposit (v1.2.10.1):** `scripts/gateway_deposit.py` deposits a small amount of USDC (at most 5 per run) from a business's agent wallet into Circle's Gateway Wallet, by hand. It writes the audit row first, then sends an exact-amount `approve`, then `deposit`, each after a typed `yes`, and it sends nothing if any chain read fails or looks wrong. It was run once on the original business on Oct 15 (3 USDC, see [Traction](traction.md)). It only deposits: nothing is spent from the Gateway balance, and no decision uses it
- **Maker-checker (v1.3.0):** every invoice records who submitted it (the admin's wallet, or the id of the API key). The admin site and `GET /admin/invoices/{id}/escalation?purpose=approve` refuse to hand the release key to the wallet that submitted that invoice; rejecting it or returning it to the agent stays open, because neither releases money. A release, reject or return claims the invoice row first, so two clicks cannot both act. The contract has no such rule: a wallet that builds the `approveEscalation` call by hand gets past the site, and then the server records it as it happened, flags it as `maker_checker_bypass` in the activity log and returns a warning. Invoices from before v1.3.0 have no recorded submitter and are not blocked. In a business where the owner submits everything from the admin site, the owner can reject or return an escalation but not release it; invoices submitted through the vendor portal or an API key can be released
- **Pause with a reason (v1.3.0):** the admin site asks for a reason (3 to 200 characters, shown publicly) before it asks the wallet to sign `setPaused`. The server checks the contract really is in the claimed state, then logs the reason in the activity log and in the signed ledger (`ADMIN_PAUSED` or `ADMIN_RESUMED`, with the transaction hash). If the ledger cannot be written the pause still stands and the answer says so. A banner with the reason shows on every page of the admin site and the vendor portal (not the business registration page) while paused (`GET /pause-status`; unreadable is shown as unknown, never as active). The payment step reads the pause state right before it hashes anything and pays nothing if it cannot read it. A paused invoice is held with the marker `held_because: paused` and can be re-run after payments resume. A shadow approval while paused is refused and the invoice keeps waiting for the owner. Pausing never blocks a person's own approve, reject or return of an escalation. Only the approver's wallet can sign in to the admin site, so the same wallet pauses and resumes
- **Figures written by code (v1.3.0):** `agent/figures.py` (`render_figures`) is the only source of figures for the model's escalation narrative. The prompt gives the model placeholders such as `{amount}` and tells it to write no digits; the text is accepted only if it has no digit of its own and no unknown placeholder, and the placeholders are then filled by code. Otherwise the code-written reason is stored instead, with a line saying the narrative was withheld, so no model-made number is ever stored or hashed
- **Invoice metrics on the proof page**: invoices processed, USDC paid and duplicates caught, split by origin (`agent`, `manual`, `demo`) so hand-run payments and demo runs never count as agent traffic
- **Rollout records (v1.3.1.2):** [`docs/rollouts/`](rollouts/README.md) has one record for each thing run live: what ran, the transaction and decision hash, what failed or was not captured, and what changed afterwards. Failures stay in.
- **Demo path (v1.3.1.1):** an owner signed in with the admin wallet presses "Load demo data" on the Invoices tab (`POST /demo/seed`). It adds a demo vendor paid at the owner's own wallet, a 0.01 USDC purchase order with its receipt, and three invoices the agent decides through the real pipeline: one matching, one with no purchase order, one with the wrong amount. Until the owner approves the demo vendor on-chain all three escalate with the real written reason; once approved, the matching one is paid 0.01 USDC to the owner's own wallet. Every demo row is origin `demo`: labelled on the feed, left out of the Paid, Held and Escalated totals, never traction. At most two runs a day per business. The proof page has a "Try it in 5 minutes" section.
- **Outcomes (v1.3.1):** a public `GET /outcomes` and a block on the proof page for live invoices: how many the agent decided with no person (paid or held), how many it escalated (waiting, released, rejected), how often a person settling an escalation rejected it, duplicates caught, invoices processed, USDC paid, and the median seconds from submission to confirmed payment. Own and outside businesses are separate, the origins `agent`, `manual` and `demo` are never summed, shadow figures are kept apart, and the page states in code-written words how many outside businesses are confirmed. Every figure comes from one SQL statement that the response returns next to it (`queries`, with `definitions`), so it can be reproduced. A rate or median with nothing behind it is null, never a success

- **Milestone escrow contract (v1.3.2):** `MilestoneEscrow.sol` holds USDC for one contractor job and releases it per milestone. The milestones and their `requirementsHash`es are fixed in the constructor; the agent can release a Pending milestone only after committing the decision in an earlier block (the commitment is bound to this contract, the chain, the milestone, the evidence hash and the reasoning hash), and only up to its `agentReleaseLimit`; anything above it can be released only by the approver. The approver can always reject, override and pause, and can withdraw only the balance that Pending milestones do not need. Deployed on testnet as a reference deployment and covered by 42 Foundry tests. Since v1.3.2.1 the API can register and read an escrow (next item); nothing sends a transaction to it. See [Contracts](contracts.md)
- **Escrow registration, reads and an evidence dry run (v1.3.2.1):** `POST /admin/escrows` registers an escrow that is already deployed, only if the contract itself says its agent is this business's agent wallet, its approver is the signed-in wallet and it holds this system's USDC; `GET /admin/escrows`, `GET /admin/escrows/{id}` and the public `GET /escrows` and `GET /escrows/{address}` read it from the chain (an unreadable chain is null, never zero). `POST /admin/escrows/{id}/evidence-check` reads one GitHub pull request and returns its facts and the evidence hash they give, writing nothing and sending nothing to the chain. Evidence is fetched by `agent/safe_fetch.py` under fixed rules: https on port 443 to `api.github.com` only, every resolved address and the address actually connected to must be public, no redirects, a 256 KB cap and a 6-second limit, and no proxy from the environment. A merged pull request shows that code was merged, not that the requirements are met

**Planned** (see the [Roadmap](roadmap.md) for order and status; nothing below is built)

- Gasless spending from the Gateway balance (the balance read and a manual deposit are built)
- Treasury: economics-gated yield sweep via a pooled USYC wrapper, continuous vendor screening, other-currency invoices
- Agent-to-agent reference client for vendors (demo runs labelled `demo`)
- Invoice intake from PDF or email (a person confirms every amount), a Telegram status bot, receivables
- Contractor milestone escrow in the product: a backend module that commits and releases through the agent wallet, the decision record for each release, admin actions to fund, withdraw and override, and a proof-page view (the contract, the registration and reads, and the evidence dry run exist; nothing sends a transaction to an escrow)
- Moving the original business onto a factory contract (optional)
- A self-held agent wallet for technical users, and rotation of the ledger key as a ledger entry
- Laya fast-path decision model (built separately, not wired in)
