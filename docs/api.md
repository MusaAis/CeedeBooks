# API

Run with a **single worker**: `uvicorn backend.main:app` (the rate limiter is per-process).

**Access model.** Send the key in an `X-API-Key` header. Keys are created on the server with `python3 scripts/create_api_key.py create --role buyer --label <name>` (or `--role vendor --vendor-id N`), shown once, and stored only as SHA-256 hashes. `/decisions/*` needs no key.

**Businesses (v1.2.8.1).** A key, a vendor session and an admin session each belong to exactly one business, and every query is scoped to it: another business's ids answer 404, and its contract is never called. Create a key for a business with `--business <slug>` (default `ceedebooks`). The sign-in challenges (`/admin/auth/challenge`, `/vendor/auth/challenge`, `/apply/challenge`) take an optional `business` slug (default: the first business); the signed message names it, and an admin signature is accepted only if it recovers to that business's own `approver()`. Public reads (`/stats`, `/outcomes`, `/decisions`) cover every business by default and take `?business=<slug>` to narrow them. A business that is not `active` accepts no writes. New decisions use hash format 2, which also binds the business id and its contract address; older records keep format 1 and still verify.

| Endpoint | Who | Purpose |
|---|---|---|
| `POST /vendors` | buyer | Register a vendor (wallet address validated) |
| `GET /vendors/{id}` | buyer; a vendor for its own record | Read a vendor |
| `POST /purchase-orders` | buyer | Create a PO (number, vendor, amount, category). The category must be one of the business's own with an on-chain daily limit above zero (422 if unknown or without a limit, 503 if the limit cannot be read; nothing is saved). The amount is required, never defaulted. Duplicate PO numbers return 409 |
| `POST /receipts` | buyer | Confirm delivery of a PO. The role is set by the server from the key; `confirmed_by_role` in the body is rejected (422). One receipt per PO (409) |
| `POST /invoices` | buyer, or a vendor (key or wallet session) for its own `vendor_id` | Full pipeline (the submitter is recorded for maker-checker): retry guard, three-way match, decision, commit-then-pay or escalate. Always pays the wallet on file; the invoice category must match the PO's and be one of the business's own with an on-chain limit above zero; `amount_usdc` is required (no default) and an amount more than 0.01 USDC from the PO escalates; the runway is computed server-side from the pool balance and trailing spend (`treasury_runway_days` in the body is rejected). Duplicate invoice numbers return 409 |
| `GET /invoices/{id}` | buyer; a vendor for its own invoices | Status and `reasoning_hash`. Another vendor's invoice returns 404 |
| `POST /invoices/preflight` | buyer, or a vendor for its own `vendor_id` | Dry run of `POST /invoices`: returns `would_pay`, `would_hold` (also while payments are paused), `would_escalate`, `would_be_refused_by_contract` or `already_paid`, with every check and the reasons. Writes nothing (no invoice row, no audit row, no chain transaction) and returns only booleans, never balances or limits |
| `GET /admin/auth/state`, `POST /admin/auth/challenge`, `POST /admin/auth/verify`, `POST /admin/auth/logout` | public / admin session | Wallet sign-in for the admin site: a one-time challenge is signed with the wallet and accepted only if it recovers to the contract's current `approver()`. Challenge requests are rate-limited; failures count toward the failed-auth throttle |
| `GET /admin/overview`, `/admin/vendors`, `/admin/purchase-orders`, `/admin/invoices`, `/admin/actions` | admin session | Admin dashboard data (the overview includes the agent wallet's Gateway balance, or null if unreadable; each invoice row carries `held_because` and `submitted_by_you`, never who else submitted it). A buyer API key is refused (403); no session is a 401 |
| `GET /admin/invoices/{id}/escalation` | admin session | The on-chain key of an escalated invoice of the admin's own business, `can_reopen` (true only on a multi-business contract) and `submitted_by_you`. With `?purpose=approve` it answers 403 for an invoice this wallet submitted (maker-checker); `reject` and `reopen` are never refused for that reason |
| `POST /admin/actions` | admin session | Records an on-chain admin transaction after the wallet sent it (`set_vendor`, `set_category_limit`, `set_paused`, `approve_escalation`, `reject_escalation`, `reopen_escalation`, `accept_approver`). The server checks the chain itself (to the contract, from the admin, successful); settling or reopening an escalation also needs the on-chain event to carry that invoice's own reasoning hash. `reopen_escalation` works only on a v2 contract and then runs the stored invoice through the pipeline again (new reasoning, new hash, every limit and check). `set_paused` also needs `paused` (the state the transaction set) and a `reason` of 3 to 200 characters, and is refused (422) if the contract is not in that state or (503) if it cannot be read; it writes the ledger entry and the banner record. Approving or rejecting claims the invoice row (`escalated` to `paid` or `rejected`) so a second settlement answers 409; an approval by the wallet that submitted the invoice is recorded, flagged `maker_checker_bypass` and answered with a `warning` |
| `POST /admin/invoices/{id}/rerun` | admin session | Returns an invoice in `error`, or one held because payments were paused (409 while they still are), to the agent: own business only, one run at a time (claim to `retrying`), logged as `rerun_invoice`. A failed run goes back to `error` (502). Nothing is paid twice: the pipeline checks the chain first |
| `POST /apply/challenge`, `POST /apply` | public | Apply to become a vendor. A one-time challenge is signed with the payee wallet (EIP-191 `personal_sign`, nothing sent on-chain); the signature must recover to the wallet being applied for. A sign-in signature cannot be replayed here. Applications are private, 1 pending per wallet, 3 pending per IP, 5 per hour per IP |
| `POST /vendor/auth/challenge`, `POST /vendor/auth/verify`, `POST /vendor/auth/logout` | public / vendor | Vendor wallet sign-in. Only a wallet on file as a vendor gets a session (15 minutes idle, 2 hours at most, one live session per vendor); the challenge answers the same for every address. Send the token as `Authorization: Bearer ...`. A session is a vendor principal: it can use the vendor routes above, never `/vendors`, `/receipts`, `/purchase-orders` or `/admin/*` |
| `GET /vendor/me` | vendor | The vendor's own record, on-chain approval, purchase orders (with receipt and invoiced flags) and invoices. Nobody else's |
| `GET /admin/applications`, `POST /admin/applications/{id}/accept`, `POST /admin/applications/{id}/reject` | admin session | Review applications. Accepting only creates the vendor record: it still cannot be paid until the admin approves its wallet on-chain |
| `GET /.well-known/agent.json` | public | Machine-readable manifest: the vendor flow step by step, endpoints with their roles, and the guarantees, so another agent can discover how to invoice CeedeBooks |
| `GET /decisions/{hash}` | public | The stored audit record, including the full reasoning text |
| `GET /decisions/{hash}/verify` | public | Recomputes the SHA-256 of the stored `hash_input`, and (`onchain`) checks that the same hash is in a BudgetEnforcer event of the recorded transaction |
| `GET /decisions` | public | Latest audit entries, newest first (no reasoning text) |
| `POST /business/apply/challenge`, `POST /business/apply` | public | Apply to register a business. The challenge is signed with the wallet that will own it (EIP-191, nothing sent on-chain); it cannot be replayed from a vendor sign-in or application. 1 pending per wallet, 2 pending per client, 3 per hour per client |
| `POST /business/status/challenge`, `POST /business/status` | public (signed) | An owner reads only the applications made with their own wallet, and for an accepted one the agent wallet and the factory to call |
| `POST /business/register` | public | `{application_id, tx_hash}` after the owner created the contract. Goes live only if the chain shows our factory made it, the applicant's wallet is its approver and the issued agent wallet is its agent |
| `GET /pause-status?business=<slug>` | public | `{paused, reason, by, since}` for one business, read from its contract (null `paused` when unreadable, never a guess). The reason is public; a pause made outside the site has no reason |
| `GET /businesses` | public | Active businesses with contract and agent wallet addresses, so anyone can check them on the explorer |
| `GET /operator/business-applications`, `POST /operator/business-applications/{id}/accept`, `POST /operator/business-applications/{id}/reject`, `POST /operator/businesses/{id}/external` | operator session | The home business's admin only. Accepting creates the hosted agent wallet. `external` (an outside party) is set only here and never for the home business |
| `POST /invoices` with `mode: "shadow"` | buyer or admin session | A real bill mirrored as a testnet payment: needs `real_amount` and `real_currency`, cannot carry an `origin` label, and a vendor cannot submit one. If the rules say pay it is parked as `awaiting_owner` (answer `decision: "await_owner"`) |
| `POST /admin/invoices/{id}/shadow-approve`, `POST /admin/invoices/{id}/shadow-reject` | admin session | Approve pays through the normal commit-then-pay and records agree (a failed payment leaves it waiting and records nothing; while payments are paused it answers 409 and the invoice keeps waiting); reject pays nothing and records disagree. Only the business's own shadow invoices |
| `POST /admin/decisions/{hash}/verdict` | admin session | `{"verdict": "agree" or "disagree"}` on a held or escalated shadow decision of the admin's own business. One verdict per decision; a second returns 409 |
| `GET /businesses/{slug}/traction` | public | One active business: live counts of the agent's own traffic only (origin `agent`), `not_traction` with the manual and demo counts apart, shadow counts apart, shadow real-amount totals per currency, agreement `{agree, disagree, n, rate}` (`rate` null when `n` is 0), the latest paid decisions of the agent's own traffic (live or shadow, each with its `origin`) with transaction and reasoning hashes, its contract, agent wallet and own / outside / unconfirmed label. No contacts or private fields |
| `GET /admin/categories`, `POST /admin/categories`, `PATCH /admin/categories/{id}` | admin session | The business's own categories with their on-chain limits (`usable` is null when the chain cannot be read); add one by name (the server picks the id; a duplicate name in any case is 409); rename one (the id never changes). Another business's ids answer 404. The daily limit is a separate transaction the owner signs |
| `GET /admin/onboarding` | admin session | The owner's own setup checklist: agent wallet gas, pool funded, a category created with its limit set, a vendor, a purchase order. Unreadable steps show as unknown, never as done |
| `GET /.well-known/ledger-key` | public | The Ed25519 public key and key id that sign ledger entries |
| `GET /ledger/verify?business=<slug>` | public | Re-checks that business's whole chain: links, hashes, signatures, sequence, and that every decision is chained exactly once, then compares the newest on-chain anchor of its `agent()` with the chain (`anchor.status`: none, match, mismatch, short, unreadable). `fully_verified` is true only with a matching anchor. Returns the first problems found (at most 20). 503 if no key is configured |
| `GET /ledger/entries?business=<slug>&after=<n>&limit=<1-500>` | public | The signed entries after sequence `n`, exactly as stored, so a browser can re-check them |
| `POST /operator/businesses/{id}/archive` | operator session | `{archived: true or false}`. An archived business accepts no writes and is hidden from public lists and totals; still readable with `?business=<slug>` and still verifies. Never the home business |
| `GET /metrics/decisions?business=<slug>` | public | Rules verdict versus the model's second opinion over decisions that recorded one: `total`, `compared` (a model answered), `agreed`, `disagreed`, `contract_refused` and `agreement_rate` (null when nothing was compared), by origin and by business, `live` and `shadow` apart |
| `POST /demo/seed` | admin session | Loads the demo vendor, purchase order, receipt and three demo invoices into the signed-in business and runs them through the agent. Returns `run`, `label` ("demo"), `vendor_wallet` and each invoice's decision. Two runs a day (429 after); 422 if the business has no usable category |
| `GET /outcomes?business=<slug>` | public | Outcome figures for live invoices, in `by_ownership` (`own` and `outside`) then by origin (`agent`, `manual`, `demo`), never summed: `processed`, `decided_alone` (`paid_by_agent` plus `held`), `escalated` (`waiting`, `released`, `rejected`, `total`), `person_agreement` (`confirmed_agent`, `overrode_agent`, `n`, `rate`, null when no escalation has been settled), `duplicates_caught`, `volume_usdc` and `seconds_to_payment` (`median` null with none, `n`, `without_timing`). Also `outside_businesses` with a code-written statement, `shadow` (apart), `definitions` and the SQL of each figure in `queries`. Counts only; archived businesses leave the aggregate |
| `POST /admin/escrows` | admin session | `{address}` of an escrow that is already deployed (the server never deploys). Accepted only if the contract says its agent is this business's agent wallet, its approver is the signed-in wallet and its USDC is this system's, and it is not the business's own budget contract; 503 if the chain cannot be read, 409 if the address is registered (by anyone), 10 registrations an hour per wallet. Logged as `register_escrow` |
| `GET /admin/escrows`, `GET /admin/escrows/{id}` | admin session | This business's escrows with the chain read: roles, USDC addresses, release limit, balance, pending and withdrawable amounts and each milestone's amount, requirements hash, status and whether the agent may release it. `chain_ok` false and `escrow` null when the chain cannot be read. Another business's id answers 404 |
| `POST /admin/escrows/{id}/evidence-check` | admin session | `{owner, repo, pr_number}`: a dry run that reads one GitHub pull request through the fetch rules and returns `facts` and `evidence_hash` (the SHA-256 of the facts in canonical JSON). Writes nothing, sends nothing to the chain. 422 for a refused address or input, 502 if GitHub cannot be read, 10 a minute per wallet and 30 an hour overall |
| `POST /admin/escrows/{id}/milestones/{index}/decision` | admin session | `{owner, repo, pr_number}`: a dry run of the agent's verdict on one milestone (index 0 to 49) with one pull request as evidence. Returns `verdict` (`release`, `hold` or `escalate`), the reason, each check, the milestone, the `facts` and the `evidence_hash`. Writes nothing and sends nothing. 404 for an unknown milestone, 409 for one already released or rejected, 422 for a refused input or an escrow whose agent is not this business's wallet, 502 if GitHub cannot be read, 503 if the chain cannot be. Shares the evidence rate limits |
| `POST /admin/escrows/{id}/milestones/{index}/release` | admin session | The same body plus the `evidence_hash` from the dry run (409 if GitHub now says something else). Records the verdict first (503 without a ledger key); on `release` it claims the milestone (409 if a release is in progress or done), sends `commitDecision`, waits, sends `releaseMilestone` and waits, then reads the milestone back. `hold` and `escalate` are recorded and send nothing. A failed step answers 502 and flags the record `contract_refused`; if a confirmation times out but the chain shows the milestone released it answers 200 with a warning. Logged as `escrow_release`, `escrow_hold` or `escrow_escalate` |
| `GET /admin/escrows/{id}/releases` | admin session | The release attempts for this escrow: milestone, status (`claiming`, `released`, `failed`), who asked, the evidence and reasoning hashes and the Circle transaction id |
| `GET /escrows/{address}/decisions` | public | The agent's recorded decisions on one registered escrow, newest first (`?limit=` 1 to 50, default 20): `reasoning_hash`, `action` (`ESCROW_RELEASED`, `ESCROW_HELD`, `ESCROW_ESCALATED`), `milestone`, `amount_usdc`, `timestamp`, `chain_tx_hash` (null when nothing was sent). No reasoning text: fetch a record by hash from `/decisions/{hash}/verify`. Only the registering business's own records are listed. 404 for an unregistered address or an archived business |
| `GET /escrows`, `GET /escrows/{address}` | public | Registered escrows of active businesses (`?business=<slug>`), and one with its chain read. No registering wallet or other private field. Unregistered addresses and archived businesses answer 404 |
| `GET /stats` | public | Counts of paid, held and escalated agent decisions (demo and shadow decisions and manual entries are reported separately and never counted as agent decisions), plus `submissions`: invoices processed, USDC paid and duplicates caught, split by origin |

Hardening: amounts are exact decimals (positive, at most 6 places); request bodies over `MAX_BODY_BYTES` return 413; per-IP rate limit (`RATE_LIMIT_PER_MIN`) and a stricter limit on failed keys (`FAILED_AUTH_PER_MIN`) return 429; CORS allows only `CORS_ORIGINS` (default `https://ceedebooks.xyz`). Behind a reverse proxy set `TRUST_PROXY=1` so limits apply per real client.

Deploy steps (nginx + certbot + systemd, and the admin site): [deploy/DEPLOY.md](../deploy/DEPLOY.md).

Limits: runway uses ledger history only (paid invoices in the last 30 days), so a fresh ledger gets the 365-day cap.

`verify` checks the stored record and, where a transaction is recorded, the matching on-chain event. Since v1.2.9 the chain itself is checked by `GET /ledger/verify` (server side); the proof page's "Verify the whole chain" button repeats it in the browser, and the head is anchored on-chain (v1.2.9.2).
