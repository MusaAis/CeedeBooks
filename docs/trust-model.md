# Trust model and limits

Read this before relying on the system. What the contracts guarantee, what they do not, and who holds which key.

## Trust model and limits (read this before relying on it)

- **What the contract guarantees:** only registered vendors are paid, within per-transaction, daily and per-category limits, once per invoice, and only after a commitment from an earlier block. The agent cannot change any of that, whatever it is told.
- **What it does not guarantee:** that an invoice is genuine. A human approves vendors and confirms receipts; the three-way match is only as honest as those people.
- **One operator.** The agent wallet is a Circle developer-controlled wallet under one account. "A second wallet" is not an independent agent.
- **The audit log is a database.** Each record's hash is checked against an on-chain event, and since v1.2.9 each business's decisions are also hash-chained and signed, so an edited, deleted or reordered row is detected by `GET /ledger/verify`. Limits: the signing key sits on the same server as the database, so someone holding both could rewrite the chain, and the newest entries could be dropped together with their rows. Since v1.2.9.2 each business's agent wallet anchors the chain head on-chain. **What an anchor proves:** the chain up to that sequence had exactly that head by that block, so rewriting or dropping any of those entries afterwards fails the check. **What it does not prove:** anything about entries after the newest anchor; or that the anchor is independent of the operator. The agent wallet is a separate wallet run by the same operator, so someone controlling everything could anchor a rewritten history at a higher sequence (the contract keeps only the latest anchor per sender, but the earlier `Anchored` events stay on the explorer and show it). It is also not proof that a decision was correct, only that it was recorded and not altered. Backfilled entries prove nothing about the period before the backfill.
- **The admin key.** The approver is a wallet held off the server. If it is lost, nobody can approve vendors or change limits.
- **Testnet.** Everything runs on Arc Testnet with test USDC. No outside business or paying user yet; every payment so far is self-owned.
- **Two businesses, both ours.** The backend is multi-tenant and onboarding works on testnet: our own test business went through it (application, acceptance, hosted agent wallet, factory transaction, on-chain verification, funding). No outside business has used it. Isolation between businesses is enforced in code and covered by cross-business denial tests and, for the factory event, a real factory on a local node.
- **Hosted agent wallets.** See [Custody trade-off](#custody-trade-off): for businesses we onboard, we run the agent wallet.
- **Shadow mode is a mirror.** Its payments are testnet USDC and its real amounts are what the owner typed in; nothing checks them against a bank. The agreement rate is only as meaningful as its `n`, and an owner who approves everything produces 100%.
- **Gateway deposits sit outside the contract.** USDC deposited into Circle Gateway comes from the agent wallet's own balance, not the pool, and `BudgetEnforcer`'s limits do not apply to it. The deposit script caps a run at 5 USDC, and the amount should stay small. Nothing spends from the Gateway balance yet.
- **Key custody (checked in v1.2.9.4).** Every agent transaction is signed by a Circle developer-controlled wallet; no raw wallet key is held by the service. The only raw key it reads is `LEDGER_SIGNING_KEY` (Ed25519, signs ledger entries, moves no money). `DEPLOYER_PRIVATE_KEY` is not required and nothing signs with it; it has been removed from the live server's `.env`, and holds no power over any contract since the approver rotation (see [Contracts](contracts.md)). The Circle entity secret and API key do sit in the server `.env`: whoever reads that file can act as every business's agent, within each contract's rules (see Custody trade-off).
- **The model.** A language model is used in two places: it writes the narrative when the rules escalate an unregistered vendor, and it gives a second opinion that is recorded and hashed. Neither can release, block or change a payment, and the second opinion waits at most 3 seconds. Since v1.3.0 the narrative may use figures only through code-filled placeholders; a reply with its own digits is replaced.
- **Oversight limits (v1.3.0).** Maker-checker is enforced by the API and the admin site, not by the contract (it has no such rule), so someone who builds the release transaction by hand is not stopped; the server records it and flags it. An invoice with no recorded submitter (made before v1.3.0) is not blocked. The pause itself is the contract's own `paused` flag, and the reason beside it is a record in our database and ledger that the contract does not check. The pause reason and the banner are public.
- **Outcome figures (v1.3.1).** They are counts from our own database, so they are exactly as honest as its rows: a person's release is recognised by the admin action the server recorded for that invoice, and an invoice the agent paid after "Return to agent" counts as the agent's. "Person agreement" is the share of settled escalations a person rejected; a release overrides the agent's caution, and an owner who releases everything produces 0%. The median covers only payments stamped at payment time (v1.3.1 on), so earlier payments are counted as `without_timing`, never estimated. Shadow figures and the own, outside and `demo` buckets are never added together.
- **The escrow contract (v1.3.2).** It enforces who can release what, in which order and up to which amount, not that the work was done: the evidence hash is a record, and anything above `agentReleaseLimit` needs the approver. Its agent and approver are wallets of one operator, like the rest of the system. The only deployment is a reference with no funds and no engagement, the agent's release path for it has been run live once (a 0.1 USDC release of milestone 0 with a stand-in merged pull request, all wallets ours; other milestones and every reject, override, withdraw and pause have not), and its explorer source verification failed (the bytecode matches a local build). The server never deploys escrows and will never hold the approver key. The fetch rules for evidence are built (v1.3.2.1): one allowlisted host, public addresses only (checked on resolution and on the connection actually made), no redirects, size and time caps. Limits: the check trusts GitHub's answer and the DNS of `api.github.com`; a merged pull request is not proof that a milestone is met; the agent's release verdict rests on one merged pull request and on the escrow's own state, so a person who controls the repository and the escrow's approver can make a release happen; the agent's key is the operator's Circle wallet (the same operator as everything else); and the release limit is the contract's, so anything above it always needs the approver.
- **Public reasoning.** `GET /decisions/{hash}` returns the full reasoning text, so no private data belongs in it.

## Custody trade-off

For the businesses we onboard first, **we run your agent's wallet.** It can only pay your approved vendors within your limits, and you can revoke it any time. You keep the owner wallet that controls the money and the limits. This was a deliberate choice: it lets a business with no technical staff get started in minutes, with no keys or servers to run.

What the agent wallet can and cannot do, all enforced by your contract and not by us:
- It can pay a vendor your wallet has approved, up to your per-payment, daily, per-category and (on the multi-business contract) weekly limits, once per invoice, and only after a decision was committed in an earlier block. It can also escalate a payment for you to decide and log a refusal.
- It cannot withdraw funds, add or approve vendors, change a limit, pause, or take over the contract. Those belong to your owner wallet, which we never hold. You can replace the agent wallet at any time.
- It holds only the small amount of USDC you send it for network fees (plus anything the operator deposits into Circle Gateway with the manual script, at most 5 USDC per run, which the contract's limits do not cover). Your money sits in your contract, not in the agent wallet.

What it costs you in trust: the agent wallets are controlled by CeedeBooks through one Circle account, so they are **a separate wallet per business, but the same operator**. If that account were compromised, an attacker could act as every business's agent at once, limited by each contract's rules. A self-held agent (you run the signer, we hold nothing) is a possible later option for technical users and is not built.

Each business's contract and agent wallet addresses are public on the proof page and at `GET /businesses`, so anyone can check them on the explorer.

## Design notes for reviewers

- **`invoiceKey` excludes amount on purpose.** It's derived from `(vendor, invoiceNumber)` only, so altering the amount on a resubmission can't get a second payment through.
- **`categoryDailyLimit` defaults to 0.** An unregistered category is fail-closed.
- **Escalated invoices are locked out of `pay()`.** Once `escalate()` runs for a key, `pay()` for the same key reverts with `"Invoice escalated"`.
- **Gas and off-chain costs (LLM inference, hosting) are not `pay()` categories.** Only transactions that move USDC through the contract belong there; the rest are off-chain ledger entries, never a phantom "paid".
- **A retry can't pay twice.** `process_invoice()` checks the contract's own `paid` mapping first.
- **A transaction ID isn't a result.** Every commit, payment, and escalation is confirmed to a terminal state before anything is logged as succeeded — see [bug #8](known-issues.md).
- **Escalation reasons come from the rules, not the model.** A failed match is escalated with the rule that failed; the model is asked to narrate only vendor-registration escalations (through placeholders, with figures filled in by code), and separately for a recorded second opinion that never acts.
